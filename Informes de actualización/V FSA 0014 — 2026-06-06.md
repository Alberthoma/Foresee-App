# Informe de Actualización — V FSA 0014
**Fecha:** 2026-06-06

---

## Solicitud del usuario

Al decir `"Recibí 90.284,50 Utilidad aplicación Chase guardar"`, la app registró **90.28** en lugar de **90,284.50**.

---

## Causa identificada

El reconocimiento de voz transcribió el número en **formato europeo/latinoamericano**:
- `.` como separador de miles → `90.284` = 90,284
- `,` como separador decimal → `,50` = .50

El fix de V FSA 0013 solo normalizaba el formato americano (`15,000` con coma de miles).  
La Estrategia C del parser capturaba `"90.284"` como primer patrón `\d+[.,]\d+` y hacía `parseFloat("90.284")` = 90.284 → formateado a 2 decimales = **90.28**. El `,50` quedaba fuera del match.

---

## Modificación realizada

### JS — `parseVoiceInput()` (`index.html`) — sección MONTO

Se añadieron dos reglas de normalización **antes** de las estrategias de monto:

```js
// Antes (solo formato americano)
rem = rem.replace(/\b(\d{1,3}(?:,\d{3})+)\b/g, (m) => m.replace(/,/g, ''));

// Ahora (cubre los tres formatos)

// 1. Europeo completo: 90.284,50 → 90284.50
rem = rem.replace(/\b(\d{1,3}(?:\.\d{3})+),(\d{1,2})\b/g, (_, int, dec) =>
  int.replace(/\./g, '') + '.' + dec
);

// 2. Solo miles europeo: 90.284 → 90284
rem = rem.replace(/\b(\d{1,3}(?:\.\d{3})+)\b/g, (m) => m.replace(/\./g, ''));

// 3. Americano: 15,000 → 15000 (ya existía en V FSA 0013)
rem = rem.replace(/\b(\d{1,3}(?:,\d{3})+)\b/g, (m) => m.replace(/,/g, ''));
```

**Clave de la distinción:** la regex `\d{1,3}(?:\.\d{3})+` solo activa cuando hay **exactamente 3 dígitos** después del punto (patrón de miles). Un decimal como `90.50` (2 dígitos) no hace match → no se toca.

**Flujo corregido para `"90.284,50"`:**
1. Regla 1 captura `90.284,50` → produce `90284.50`
2. Estrategia C captura `90284.50` → `parseFloat("90284.50")` = **90284.50** ✓
